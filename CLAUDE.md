# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

**Database**: `DATABASE_URL` points at a hosted Supabase Postgres — no local DB needs to be started. `docker compose up -d` only exists as a local-Postgres alternative if you deliberately point `DATABASE_URL` at localhost.

**Run the development server:**
```bash
# From project root, with venv activated
uvicorn app.main:app --reload
```

**Activate virtual environment (Windows):**
```bash
venv\Scripts\activate
```

**Database migrations:**
```bash
# Apply all pending migrations
alembic upgrade head

# Create a new migration (auto-detect model changes)
alembic revision --autogenerate -m "description"

# Rollback one migration
alembic downgrade -1
```

**Install Playwright browsers (first-time setup):**
```bash
playwright install chromium
```

**Run the agent eval harness (from project root — `.env` resolves against CWD):**
```bash
python eval/run_eval.py run --label baseline                 # all 30 queries, with LLM judge
python eval/run_eval.py run --label quick --no-judge         # rule checks only
python eval/run_eval.py run --label x --only relevance_gating  # one category
python eval/run_eval.py run --label x --ids relax_zh_003,clear_en_002  # specific cases
python eval/run_eval.py compare eval/runs/A.jsonl eval/runs/B.jsonl
```

## Environment Variables

Create a `.env` file in the project root. Required variables (see `app/config.py`):

```
DATABASE_URL=postgresql://postgres:password@localhost:5432/pickwise_v2
DB_POOL_SIZE=10                             # optional — pooled connections kept open (see app/database.py)
DB_MAX_OVERFLOW=20                          # optional — extra connections under load; size + overflow is the hard ceiling
DB_POOL_TIMEOUT=30                          # optional — seconds waiting for a free connection before QueuePool raises
DB_POOL_RECYCLE=1800                        # optional — recycle below the provider's idle-connection cutoff
SECRET_KEY=your-secret-key
SMTP_USERNAME=your-gmail@gmail.com          # email sending — does NOT work on Render, see below
SMTP_PASSWORD=your-gmail-app-password
FRONTEND_URL=https://pickwise-v2.vercel.app        # base URL for links in emails (password reset)
BACKEND_URL=https://pickwise-v2-backend.onrender.com  #   and for the email-verification link
GEMINI_API_KEY=your-gemini-api-key
YOUTUBE_API_KEY=your-youtube-data-api-key   # optional — server starts without it
SERP_API_KEY=your-serpapi-key               # optional — market price tool's live-listings layer (SerpApi Google Shopping); catalog layer works without it
GOOGLE_OAUTH_CLIENT_ID=xxx.apps.googleusercontent.com  # optional — Sign in with Google; POST /auth/google returns 400 without it
WEBSHARE_PROXY_USERNAME=xxx                 # optional — Webshare rotating-RESIDENTIAL proxy for review transcript fetches;
WEBSHARE_PROXY_PASSWORD=xxx                 #   direct connection when unset (fine locally; Render's datacenter IP is blocked by YouTube)
```

**Email does not send from Render.** Render blocks outbound traffic to SMTP ports (25/465/587) on free instances, so `app/users/email.py`'s `smtplib` call fails instantly with `[Errno 101] Network is unreachable` — and because the send runs in a `BackgroundTasks` job, registration still returns 201 "check your email" while nothing is delivered. Registering with an email address is therefore effectively broken in production until the account is verified another way (Google sign-in sets `is_verified` directly); an HTTP-API email provider or a paid instance would fix it. The senders return a bool and log every failure at ERROR — they never raise, since nothing would see the exception. Links inside emails are built from `BACKEND_URL`/`FRONTEND_URL` — set both on Render, or they point at `localhost`. The verification link must include the `/api/v2` prefix that `main.py` mounts routers under.

`GEMINI_API_KEY` is a required setting (`app/config.py`) and is passed explicitly (`google_api_key=settings.gemini_api_key`) to every Gemini client — agent, embeddings, processor, recommendation, review processor, and the eval judge. Do **not** rely on the ambient `GOOGLE_API_KEY` / Application Default Credentials — that won't exist in Docker/production.

`YOUTUBE_API_KEY` is optional (`Optional[str] = None` in `app/config.py`) — the server starts without it; the review discovery/ingest endpoints raise 400 at call time if it's missing.

The Docker Compose DB defaults: user=`postgres`, password=`password`, db=`pickwise_v2`.

## Architecture

### Data Pipeline (core flow)
```
Feed Crawler → laptop_scrape_urls (ScrapeTarget)
     ↓
Scrape URL / Bulk Scrape → raw_scrap_laptops (RawScrapLaptop, status: pending)
     ↓
AI Processor (Gemma gemma-4-31b-it) → laptops (normalized, multi-variant)
     ↓
Embeddings (gemini-embedding-2, 768-dim) → laptop_embeddings
```

Independent of the flow above: Benchmark Scraper (PassMark) → `cpu_benchmarks` / `gpu_benchmarks` (consumed by PickScore), and the YouTube review ingestion pipeline (see `app/reviews/`):

```
discover_videos (YouTube Data API) → fetch_transcript → RapidFuzz match to laptop
     → raw_youtube_reviews (matched/pending/rejected)
     → process (45s chunks → Gemini summary + sentiment → embed) → laptop_review_chunks
     → aggregate → laptop_review_summary
```

### Module Structure

Each domain module under `app/` follows a consistent pattern: `models.py` (SQLModel tables + Pydantic schemas), `router.py` (FastAPI endpoints), and supporting files.

- **`app/users/`** — Auth (username-or-email login, Google Sign-In via ID-token verification), JWT, bcrypt, email verification, preferences (`laptop_user_preference` table, `budget` stored as `{min, max}` JSON range). Avatar gateway: `PUT/DELETE /auth/me/avatar` + public `GET /auth/avatar/{user_id}` — bytes in the separate `user_avatars` bytea table (Render fs is ephemeral; separate table so `get_current_user` never loads the blob), magic-byte validation, 2 MB cap. Google login imports the `picture` claim into the same table on create/link only (best-effort, never on returning logins — a deleted avatar must stay deleted). `questionnaire_model.py`/`questionnaire_router.py` expose the 6-step preference survey as a dynamic catalog (`GET /questionnaire?product_type=laptop`, `include_inactive=true` for admin views) plus admin-only CRUD (create/update/delete; 409 if another active question occupies the same `step_order` for the product type). Answers are still written via the existing `PUT /me/preferences`. `question_type` is a native Postgres enum (`questiontype`) — adding a Python enum member requires an `ALTER TYPE ... ADD VALUE` migration (e.g. `MULTIPLE_CHOICE` in `c8f24d1e9a37`).
- **`app/laptops/`** — 9-part laptop spec model, brands (UUID FK), customizations (bulk/pattern creation, `category_id` FK into `app/taxonomy/`), price history, hybrid vector search. `laptop_category_model.py` owns the `laptop_categories` many-to-many junction (laptops ↔ tags). `family_key.py`/`family_model.py`/`family_service.py`/`family_router.py` own the `laptop_family` grouping and the deduplication it drives (see the Laptop families section below). `Laptop.status` (`active`/`inactive`/`suspended` — same spelling as `users.status`; `LaptopStatus` in `laptop_models.py`, migration `d9e1f4a86c27`) is the listing state: plain VARCHAR like `users.status` (a new state needs no `ALTER TYPE`), defaults to `active` for every new/backfilled row, validated by a `field_validator` on `LaptopBase`/`LaptopUpdate` (SQLModel skips validation on `table=True`, so the check only bites on `LaptopCreate`/`LaptopUpdate` — which is every write path). The AI processor's upsert dict does not contain `status`, so re-processing a scraped page never resurrects a laptop an admin deactivated. `GET /laptops/?status=` filters on it (aliased to the `status_filter` argument — a param named `status` would shadow FastAPI's `status` import); **omitted means all statuses**, so the admin catalog view keeps seeing retired rows.

**`DELETE /laptops/{id}` refuses (409) while user- or pipeline-owned rows still reference the laptop** — `saved_laptops`, `conversation_laptops`, `laptop_review_chunks`, `laptop_review_summary`, `raw_youtube_reviews.matched_laptop_id` (the `_DELETE_BLOCKING_REFERENCES` list in `laptop_router.py`), mirroring `brand_router.py`'s "still-referenced" 409. This is not a nicety: **every FK to `laptops.id` is `NO ACTION` — there is no `ON DELETE CASCADE` anywhere in the schema** — so without the guard those five produce a raw `IntegrityError` 500 (~50 of 276 laptops were undeletable). The other five children (customizations, embedding, price history, pick scores, category links) are derived data and *are* cleaned up, via `cascade="all, delete-orphan"` on `Laptop`'s relationships. Retiring a listing is `status: "inactive"`, not deletion — that is what the status field is for.
- **`app/taxonomy/`** — `product_type_model.py`/`product_type_router.py` (small stable set, e.g. `"laptop"`, scopes the questionnaire) and `category_model.py`/`category_router.py` (marketing/use-case tags for the frontend tag component) — both mirror `app/laptops/brand_model.py`'s CRUD shape exactly (admin-only writes, public reads, 409 on duplicate/still-referenced).
- **`app/pickscore/`** — Product-agnostic scoring engine (see PickScore section below)
- **`app/laptops/pickscore_adapter.py`** — Converts `Laptop` → `ScorableProduct`; owns laptop range DB queries (calibrated from catalog laptops, not global benchmark table)
- **`app/laptops/pickscore_router.py`** — `/laptops/calculate-score` endpoints
- **`app/embeddings/`** — `service.py` builds a natural-language document per laptop and embeds it via Gemini `models/gemini-embedding-2` (`output_dimensionality=768` pins the model's larger default down to match the `Vector(768)` column without a schema migration). `embed_text()` is the single embedding entry point for the whole app (hybrid search, RAG retrieval, review chunks, recommendation). Changing the embedding model changes the vector space — always re-run `POST /embeddings/generate-all` (and re-process any review chunks) afterwards. `router.py` exposes admin-only generate-all / generate-single / status endpoints
- **`app/recommendation/`** — `service.py` orchestrates the full recommendation pipeline (hybrid search → batch PickScore → Gemini LLM); `router.py` exposes `POST /recommendations/laptops` (auth required); `schemas.py` owns request/response models including internal `_LLMOutput` for structured Gemini output
- **`app/rag/`** (renamed from `app/conversations/`) — RAG pipeline + conversation-thread persistence, now consumed as a library by the agent (see `app/agent/` below) rather than driven by its own chat endpoint. `retrieval.py` (Module 1), `reranker.py` (Module 2), `relaxation.py` (Module 3), `gating.py` (Module 4), `evaluation.py` (Module 5 + live logging, still writes `pipeline_eval_logs` on every `search_laptops` tool call). `service.py` is conversation-thread CRUD only (`create_conversation`, `list_conversations`, `get_conversation`, `delete_conversation`). `router.py` exposes 6 `/conversations/` endpoints (all auth-required, URL prefix unchanged) — create/list/get/delete a thread, `PATCH /{id}` rename (trimmed, 400 on empty, capped at 60 chars like auto-generated titles), and `GET /{id}/laptops` returning the persisted shortlist pool as `AgentLaptopCard`s (imported from `app.agent.router` — safe one-way import — so the shape stays locked to the chat stream's `done` payload; used by the frontend to restore the shortlist rail on conversation reopen); **no `/chat` route** (removed, superseded by `POST /agent/chat`). `models.py` owns `Conversation`, `Message`, `ConversationLaptop`, `PipelineEvalLog` tables.
- **`app/agent/`** — ReAct agent built with `langchain.agents.create_agent` (migrated off the deprecated `langgraph.prebuilt.create_react_agent`), the sole conversational entry point (`POST /agent/chat`). `graph.py` owns `AGENT_MODEL = "gemma-4-31b-it"` / `AGENT_TEMPERATURE = 0.3` and the `build_agent_llm()` factory — the single source of truth for the agent LLM config; `eval/run_eval.py` imports `build_agent_llm` (and `_SYSTEM_PROMPT`) so offline evals always measure the production setup. The system prompt contains two enforcement blocks added after eval failures: **SCOPE ENFORCEMENT** (refuse all non-laptop tasks — fixed the agent doing unrelated tasks like letter-writing when asked in Chinese) and **FACTUAL GROUNDING** (never quote prices from memory — call `search_malaysian_market_price` for real numbers; work with returned `search_laptops` results before suggesting anything from memory; treat `0.0`/"unrecognized" tool values as unavailable, never borrow numbers from a different configuration). A third prompt block tells the agent to cite each result's `pick_score` as "PickScore N/100" with its top factors, and never to invent a score for unscored results. `tools/search_laptops.py` absorbs the CRS retrieve→rerank→relax→gate pipeline as a tool; after gating it batch-computes PickScore on the top-k results (same ranges+benchmarks-once pattern as `app/recommendation/service.py`) and attaches `pick_score` + a compact `pick_score_top_factors` summary to each result, plus a payload-level `score_mode` — **personalized** when the request's authenticated user has a preference row, **general** otherwise. The user binding is a per-request tool factory (`make_search_laptops(user_id)`, swapped in by `graph.py::_agent_tools()`), never an LLM-visible argument — the module-level `search_laptops` in `ALL_TOOLS` stays general-mode, which is what the eval harness imports. The system prompt tells the agent to present personalized scores as "your personalized PickScore N/100" — full 8-factor breakdowns are deliberately omitted to keep tool output within the eval judge's truncation budget. PickScore failure is non-fatal (results go out unscored); `tools/laptop_tools.py` owns `calculate_custom_apple_price` and `get_review_evidence`; `tools/market_price.py` owns `search_malaysian_market_price` — two-layer price lookup: (1) catalog layer from own DB (official `price_rm` + last 5 `laptop_price_history` snapshots; `model_code` exact match first, else RapidFuzz `token_set_ratio ≥ 75` on `product_name`, fuzzy hits carry a "closest match — verify chip generation/size" note), and (2) live-listings layer via SerpApi (serpapi.com) Google Shopping geo-targeted to Malaysia (`SERP_API_KEY`, optional; free tier ~100 searches/month — replaced Serper.dev, and before that the parse.bot iPrice integration, which lacked laptop coverage). Live-listings hygiene: RapidFuzz title-relevance ≥ 60 **plus** an accessory-keyword blocklist and a RM 800 price floor (token_set_ratio scores 100 for "<laptop name> skin/battery/…" titles, so relevance alone is not enough), max 2 listings per store so the price range reflects the market, 6-hour in-process cache on successful lookups only. Shopee/Lazada search links are always included as the last-resort fallback. `graph.py` injects the user's saved `laptop_user_preference` row (when one exists) as a `_preference_block()` system message — budget/purposes/priorities/screen/portability/brands/tech-savviness as defaults the conversation always overrides, so "recommend according to my preferences" works without re-asking the wizard's questions; the eval harness is unaffected (it builds its own agent input with no user). `graph.py`'s `run_agent()` reconstructs conversation state from the `messages`/`conversation_laptops` tables each turn (no LangGraph checkpointer) and flattens the reply through `_content_to_text()` — Gemini can return content as a list of typed blocks (`thinking` + `text`) instead of a plain string, which crashed the `messages` insert (`psycopg2 can't adapt type 'dict'`); text blocks are joined, thinking blocks dropped (fallback-only). `router.py` accepts an optional `conversation_id` (auto-creates if omitted), persists messages + the laptop shortlist pool (including `pick_score`) after each turn, and returns a structured `laptops` field alongside the text reply for frontend score badges. `POST /agent/chat/stream` is the SSE twin (same request body/auth): events are JSON per `data:` line — `meta` (conversation_id, first), `token` (append to bubble), `thinking` (model reasoning delta — extracted per chunk by `_chunk_to_thinking` and streamed on its own channel so the frontend renders a thinking flow; never persisted, and note it exposes raw reasoning to the client), `turn_reset` (discard current bubble — internal tool-call turn text; thinking is NOT discarded), `tool` (activity indicator), then `done` (conversation_id + the same `laptops` payload) or `error`; persistence happens after the stream completes via the shared `_persist_assistant_turn()`, and `graph.py`'s `stream_agent()` filters thinking blocks out of reply tokens (`_chunk_to_text` — no thinking fallback, unlike `_content_to_text`) — fresh `search_laptops` results when a search ran this turn, otherwise the persisted `conversation_laptops` pool joined to `laptops` (ordered by similarity, NULLS LAST). `AgentLaptopCard` includes `image_url` (first `image_urls` photo) for card thumbnails — looked up from the `Laptop` row in `router.py` when building cards, deliberately NOT added to the search tool's payload so image URLs never enter the LLM context.
- **`app/reviews/`** — YouTube review ingestion pipeline (all endpoints admin-only). `discovery.py` resolves channel URLs (4 formats) and discovers videos via YouTube Data API v3 (`search.list`, 100 quota units/channel, top 5 per channel); `transcript.py` fetches transcripts via `youtube-transcript-api` **v1.x instance API** (no quota cost) — routed through a Webshare rotating-residential proxy when `WEBSHARE_PROXY_USERNAME`/`_PASSWORD` are set; without it, YouTube IP-blocks datacenter hosts (Render), so `_build_api()` **raises** when the credentials are missing and `settings.environment == "production"` rather than silently falling back to a direct connection, which is indistinguishable from rate-limiting (see the failure-taxonomy section below); `matcher.py` fuzzy-matches video titles to catalog laptops (RapidFuzz `token_set_ratio`, threshold 73, compact match keys that strip `-inch`/RAM/storage and extract the chip from parens; stored `match_confidence` can exceed the threshold on rows scored by an older matcher config — run `/reviews/rematch` after matcher changes); `processor.py` chunks transcripts into 45-second windows → Gemini summary + sentiment tag (`strength`/`weakness`/`neutral`) → embed via the central `embed_text()` from `app/embeddings/service.py` (model `_CHUNK_MODEL = "gemma-4-31b-it"`, same as the agent but kept as a local constant so the review pipeline doesn't import the agent stack; 4s delay between Gemini calls); `aggregator.py` rolls up top-5 strengths/weaknesses into `laptop_review_summary`; `service.py`'s `ingest_for_laptop()` runs discovery → **match → transcript** end-to-end (retries `rejected` rows, skips `matched`/`pending`) — matching is local and free while a transcript fetch costs proxy bandwidth and wall time, and running it first also means a video with no transcript still gets a `match_confidence`, so it is visible to a triage queue sorted by confidence instead of sitting in `rejected` with a NULL; `ingest_bulk()` (`POST /reviews/ingest-bulk?limit=&skip_covered=`) runs it across the catalog one search per laptop *family* (`family_key`, now shared from `app/laptops/family_key.py` with the `laptop_family` grouping — it truncates `product_name` at the first paren — config variants share one YouTube search, since discovery costs ~`active_channels × 100` quota units per query against a 10k daily quota; `skip_covered=true` skips families that already have a matched raw review, so daily runs walk the catalog). Chunk processing and aggregation are manual admin steps (`POST /reviews/process/{id}`, `POST /reviews/aggregate/{laptop_id}`); `POST /reviews/process-bulk?limit=` (default 5, max 50) runs processing over every `matched` review that has no `laptop_review_chunks` rows yet — existing chunks are the "already processed" marker, since processing never flips the review's status, which also makes re-runs duplicate-safe; per-review failures are reported in the response without aborting the run; `POST /reviews/rematch` re-runs auto-matching on all pending rows.
- **`app/saved/`** — user wishlist. `SavedLaptop` (`saved_laptops` table, unique on `user_id + laptop_id`) + 4 bearer-auth endpoints: `GET /saved/` (full `LaptopRead` records, newest saved first), `GET /saved/ids` (lightweight heart-state check), `PUT`/`DELETE /saved/{laptop_id}` (both idempotent, 204). Migration `d7c2e94b5a18`.
- **`app/scraper/`** — Playwright-based crawlers for Apple (DOM) and Asus/ROG (`window.__NUXT__` JSON state); Acer (Magento 2 attributes table) is an **lxml parser over admin-uploaded HTML stored in `raw_product_htmls`** and never touches the network. `raw_html_model.py` owns that table, `html_ingest.py` its storage/lookup layer (product-agnostic — see the Acer section). Brand dispatch is a hardcoded `if/elif` on `brand.name.lower()` in three places — `router.py`'s feed-crawler and scrape-url branches, and `bulk_scraper.py::_dispatch_scraper` — so a new brand needs all three plus a `laptop_brands` row. **The crawler's start URL is always the brand's own `base_scrape_url` from the DB**, never client-supplied (`POST /scraper/feed-crawler` takes `{brand_id}` only; 400 if the brand has no `base_scrape_url`). After crawling, admins scrape either a whole brand (`POST /scraper/bulk-scrape`, pending + previously-failed targets) or a hand-picked subset (`POST /scraper/scrape-targets` with `{target_ids: [...]}`, which ignores `scrape_status` — an explicitly selected row is always attempted). `GET /scraper/targets` lists the crawled queue (filters: `brand_id`, `scrape_status`, `is_active`; paginated) and is what the admin selection UI reads. Both scrape endpoints share one per-target pipeline (`bulk_scraper.py::_process_target`) and return HTTP 207 on partial failure.
- **`app/processor/`** — LangChain + Gemini LLM extraction from raw scraped data into structured `Laptop` records. Also does category tagging: the extraction schema's `categories` field has the model pick 1–3 use-case tags per variant, preferring the active `categories` rows injected into the prompt as `[AVAILABLE CATEGORIES]`; unknown tags are auto-created in the `categories` table (case-insensitive match, inactive rows matched too so they're never duplicated) and linked via `laptop_categories`. Linking is additive — re-processing never removes manually-assigned tags. `POST /processor/categorize-untagged?limit=N` (admin) backfills laptops with zero category links: one Gemma call per laptop from its stored specs (via `build_laptop_embedding_text`), 5 s throttle, safe to re-run until `untagged_remaining` is 0.
- **`app/benchmark/`** — PassMark CPU/GPU scraping with PostgreSQL upsert (`ON CONFLICT DO UPDATE`)
- **`app/logger.py`** — Centralized logging service. `setup_logging()` called once in `main.py` (console + 5 MB rotating `logs/app.log`). `get_logger(__name__)` is the drop-in for all modules. `get_eval_logger()` returns the special `pickwise.eval` JSON-lines logger used by `rag/evaluation.py`. File logging is **best-effort**: if `logs/` isn't writable (container with non-root user / read-only fs), both loggers warn and fall back to console/stdout instead of crashing startup — a root-owned `WORKDIR` once took down the whole deploy via `PermissionError` in `mkdir`.
- **`app/config.py`** — `pydantic-settings` loading from `.env`
- **`app/database.py`** — SQLModel engine, connection-pool config, `get_session()` dependency, `session_scope()` context manager, pgvector extension init. **Never hold a pooled connection across slow non-database work.** The pool is explicitly sized (`DB_POOL_SIZE`/`DB_MAX_OVERFLOW`, default 10+20) because the SQLAlchemy defaults of 5+10 produced `QueuePool limit of size 5 overflow 10 reached` in production — but sizing was the symptom, not the cause: connections were being held for the length of an LLM turn or an entire background job. The rules that keep it that way: a `Depends(get_session)` session lives until the **response completes**, which for a `StreamingResponse` means the last SSE byte, so `/agent/chat` and `/agent/chat/stream` take no session dependency and bracket their reads/writes in `session_scope()` instead (`_setup_turn` → agent → `_persist_assistant_turn`, with the rows detached in between via `expire_on_commit=False`); they authenticate through `get_current_user_detached`, because FastAPI caches dependencies per request and plain `get_current_user` would keep the very connection the endpoint just gave up; `run_job` holds exactly one connection (the worker's) and `JobProgress` opens a fresh short session per `advance()` rather than pinning a second one for the job's lifetime; and agent tools each open their own `Session(engine)` for the length of one query. `pool_pre_ping` is on because managed Postgres drops idle connections silently, and the pool is LIFO so the tail of a burst goes idle and gets recycled.
- **`eval/`** — offline agent eval harness (not part of the server). `queries.yaml`: 30 bilingual queries (zh/en/mixed-Manglish) across 5 categories — clear_intent, vague_intent, constraint_relaxation, relevance_gating, tool_routing — each with expected tools / forbidden tools / budget cap / judge rubric. `run_eval.py`: runs each query through the agent in-process (same `AGENT_MODEL`/`_SYSTEM_PROMPT` as production, single-turn, no history), applies deterministic rule checks, then an LLM judge (`gemma-4-31b-it`) that grades **only against the raw tool outputs** — never its own product knowledge (the catalog is newer than any model's training data). Results land in `eval/runs/<date>_<label>.jsonl`; `compare` diffs two runs and flags regressions. All agent + judge LLM calls share one global rate limiter (default 7 RPM; `--rpm` to override) — the binding free-tier limit is the **16,000 input-TPM cap**, not the 15 RPM request cap: judge prompts carry up to ~27k chars of tool output, so runs must stay below 8 RPM or high-context tool_routing cases 429 (this contaminated the 2026-07-18 gemma-baseline run with 1 failed + 3 unscored entries). Judge failures after 3 retries mark the entry ⚠️ unscored — runs with unscored entries must not be used for compares. Tool outputs are truncated per-output (4,500 chars each, 27,000 total — sized so a full 5-result `search_laptops` payload with pick_score fields survives intact) — never head-truncate the joined blob, or evidence in later tool calls becomes invisible and grounded responses get falsely judged as fabrication.

### Key Design Decisions

**Background jobs for long batch operations** (`app/common/job_model.py`, `job_service.py`, `job_router.py`): `POST /scraper/bulk-scrape`, `/scraper/scrape-targets`, `/processor/process-pending` and `/processor/categorize-untagged` **return `202 Accepted` with a job envelope, not a result** — they used to hold the connection open for ~8 minutes (5 s throttle × 100 records), which risks proxy timeouts and gave no progress. The 202 body carries `job_id`, `total_count`, `estimated_seconds`, `estimated_completion_at` and `poll_url`; poll `GET /jobs/{job_id}` until `status` is `completed`/`failed`. The old synchronous report (including `log_file` and per-URL results) is preserved verbatim in the finished job's `result` field, so nothing was lost — but this **is a breaking change for any existing caller**.

Key invariants: `background_jobs` is a **table, not an in-process dict** — the UI polls for minutes and Render restarts on every deploy, so an in-memory registry would 404 mid-poll and break outright under multiple uvicorn workers. `run_job()` opens **two** sessions, neither of them the request's (that one is closed once the response is sent): one for the worker, one for job bookkeeping, so a poisoned worker session cannot also destroy the error report. A `finally` block guarantees a terminal status, and `reset_stale_jobs()` (called from a `startup` hook in `main.py`) fails anything orphaned by a restart — between them a job can never be permanently stuck in `processing`. Per-item failures increment `failed_count` and append to `errors[]` **without** failing the job: a run that finishes is `completed` even if every item failed, so the UI must check `failed_count`, not `status`. Endpoints validate up front (unknown brand/target ids 404 before a job row exists) so a bad request never becomes a failed job. `/jobs` is deliberately not under `/scraper` — jobs come from the processor too. `/reviews/process-bulk` is still synchronous and is the remaining conversion candidate.

**Admin lockout guards** (`app/users/admin_router.py`): an admin cannot demote or deactivate **themselves** (403, `SELF_DEMOTION_MESSAGE`), and the **last active admin** — `role == "admin" AND status == "active"` — cannot be demoted or deactivated by anyone (400, `LAST_ADMIN_MESSAGE`). Only *demotions* are checked; promoting, re-affirming an existing admin role, and re-activating are always allowed. In practice the last-admin check mostly backs up the self-guard (the caller is always an active admin, so any other active admin puts the count at ≥ 2) — it is kept because it is the check that holds the invariant if the acting identity or status enforcement ever changes. `assert_can_delete_user()` exists for the **DELETE /users/{id} route that does not exist yet**; wire it in when that route is added rather than re-deriving the rule.

**`alembic/env.py` must import every table module — this is a data-loss guard, not tidiness.** Autogenerate diffs the live DB against `SQLModel.metadata`, and a model whose module was never imported is simply absent from that metadata, so alembic concludes the live table should be **dropped**. Three tables (`saved_laptops`, `laptop_pick_scores`, `user_avatars`) sat in exactly that state until 2026-08-05; anyone running `--autogenerate` would have generated `DROP TABLE` for all three. Importing *any* name from a module registers all of its tables, so one import per module is enough — that is why `User` alone covers `LaptopUserPreference`. **Run `alembic check` before trusting an autogenerated migration**; it prints the same diff without writing a file, and should report "No new upgrade operations detected."

**Model declarations must match the live column types.** `alembic check` also flags type/nullability drift, and applying those diffs blindly is destructive in subtle ways — a `budget` column declared `JSON` while the DB holds `JSONB` would generate an ALTER that silently downgrades the column and loses JSONB indexing/operators. Fixed 2026-08-05 by making the models describe reality: `laptop_user_preference.budget` → `Column(JSONB)` (its siblings `purpose`/`priorities`/`screen_size`/`brand_preferences` genuinely *are* plain `json` — do not "upgrade" them, that creates new drift), and `agent_run_logs.user_message`/`reply_text`/`error_message` → `Column(Text, …)` with `tool_calls` → `Column(JSONB, nullable=False)`. No migration was needed; the DB was already right.

**Circular import resolution — every model module must be importable on its own.** `Laptop`, `LaptopCustomization`, and `Category` all name each other as *strings* in their relationships, and SQLAlchemy resolves a string only against a class that has actually been imported. Importing one of them alone therefore used to blow up at mapper-configure time with `InvalidRequestError: expression 'X' failed to locate a name` — which is what any standalone script, test, or eval run does. The fix is symmetric: `TYPE_CHECKING` guards at the top (for type checkers) plus a **deferred import at the bottom of all three modules**, after their own classes exist, so whichever one is the entry point pulls the other two in. Adding a relationship to `Laptop` whose target lives in another module means adding that module to the bottom block — or, better, declaring the table in `laptop_models.py`.

`LaptopPickScore` is declared in `laptop_models.py` for exactly that reason and re-exported from `pickscore_general.py` (so `from app.laptops.pickscore_general import LaptopPickScore` still works for `pickscore_router.py` and `alembic/env.py`). It cannot use the bottom-import trick: `pickscore_general` imports `pickscore_adapter`, which imports `laptop_models`, so a bottom import of `pickscore_general` deadlocks with a half-initialized `pickscore_adapter` whenever *that* module is the entry point. Table classes whose module has runtime dependencies back into the laptop stack belong in `laptop_models.py`, not next to their service logic.

**GPU resolution has three proxy paths, one flag**: `_score_gpu()` in `app/pickscore/engine.py` sets `flags.gpu_score_is_proxy = true` for all of them, and writes the `gpu` factor note saying which one ran. (1) *Apple* — PassMark has no separate GPU entries for Apple ARM chips, so the brand short-circuits to the CPU score. (2) *Integrated graphics* — a GPU string with no model-number token ("AMD Radeon Graphics", "Intel Arc Graphics") identifies no specific part, so any fuzzy match lands on the nearest-looking row; `resolve_gpu_benchmark()` in `benchmark_service.py` routes these through `_INTEGRATED_GPU_BY_CPU`, keyed on the CPU model, which always has a number to anchor on. That map is filled by hand — add entries only via `python -m app.scripts.audit_integrated_gpu`, which prints the worklist by laptop count and validates that each value resolves at ≥0.95 confidence. (3) *Unresolved* — still scored a neutral 50, but flagged, because 50 outranks a real RTX 5060 under the current `gpu_mark` ceiling. The flag is reused rather than split because `get_ranking_for_use_case` already demotes it in the gaming sort and all three deserve that; splitting them means a `gpu_resolution` field on `PickScoreResponse.flags` and a change to every consumer.

**Desktop GPU names are rewritten to their laptop variant at read time** (`_laptop_variant` in `benchmark_service.py`): every row in this catalog is a laptop, so a GPU string naming a desktop part is always wrong. Acer's source writes `GeForce RTX 5060` where ASUS writes `GeForce RTX 5060 Laptop GPU`, which scored identical silicon 23% apart by brand. The rewrite is an **exact** match after stripping the ` laptop gpu` suffix, never fuzzy — `geforce rtx 5070` must not win `geforce rtx 5070 ti laptop gpu`. Seven strings across 15 laptops are affected; check them with `python -m app.scripts.audit_integrated_gpu --rewrites` before trusting a change. This is deliberately *not* a data fix: patching `gpu_model` in the DB would be silently overwritten by the next Acer ingest, and nothing would alert you. Where a model's laptop variants differ by VRAM, `_GPU_VARIANT_OVERRIDES` pins the right row — currently the Aspire 7 `A715-59G-54Q6`, whose RTX 3050 is the 4GB part (9503, not the generic row's 12003). That map is keyed on the GPU string, not the SKU, so a second bare-`RTX 3050` machine with different VRAM would need the two separated.

**Benchmark range calibration**: `get_laptop_ranges()` in `app/laptops/pickscore_adapter.py` returns, per factor, `{min, max, values}` — `values` being that factor's sorted value across every active laptop, which is what `_normalize` ranks against (see "Normalization is percentile rank" below). It derives CPU/GPU marks by fuzzy-resolving models that are actually in the catalog (`laptops` table), not from the global PassMark tables. The GPU side resolves `(cpu, gpu)` **pairs** through the same `resolve_gpu_benchmark()` the engine uses, not GPU strings alone — an anchorless GPU name is only resolvable through the CPU it is fused to, and sharing the function is what keeps Apple out of the denominator without a brand special-case. Filling `_INTEGRATED_GPU_BY_CPU` therefore moves the `gpu_mark` floor, so re-check the range (`python -m app.scripts.dump_pickscore`) before regenerating scores. This prevents desktop/server CPU scores (200,000+) from collapsing all laptop scores toward zero. Falls back to the global PassMark table only if no catalog models resolve successfully.

**One price curve, attenuated by budget** (`_score_price` in `app/pickscore/engine.py`): personalized mode used to return a flat `100.0` for any price within the stated budget. Once `_normalize` moved to percentile that put the two modes 47 points apart on the same machine (reference laptop: 52.9 general, 100.0 personalized), in the mode that matters most — the personalized score is the "For you" number, and ADR-0006 positions PickScore as a per-user buy indicator rather than a ranker. It also meant price stopped discriminating exactly where it should: every affordable laptop scored 100, so the highest-weighted factor in `office_study` and `general_use` (weight 9) added an identical constant to every candidate. Both modes now start from the same inverse percentile, and `DECAY_K` multiplies that base rather than subtracting from a constant — same meaning (zero at 50% over budget), applied to a real score. **The percentile is always against the whole catalog, never the affordable subset** — ranking a laptop only against what one user can afford would give the same machine a different price score for every visitor, and could not be precomputed or compared across users.

Personalized scores are computed live and **`generate-all` does not regenerate them** — `generate_all_pick_scores` passes `user_pref=None`, so `laptop_pick_scores` is general-mode only. The one place a personalized score is persisted is `conversation_laptops.pick_score`, a snapshot written by `agent/router.py` from whatever mode `search_laptops` ran in; those rows are replaced on the thread's next search, so a reopened conversation can show pre-change numbers until then.

**Normalization is percentile rank, not min-max** (`_normalize` in `app/pickscore/engine.py`, ADR-0011): each of the six normalized factors scores by its position within the catalog's own distribution for that factor — `(below + tied/2) / n × 100`, taking the midpoint of a tied block so identical configurations score identically instead of depending on sort order. `inverse=True` (price, weight) subtracts from 100 as before. Min-max set every factor's scale from exactly two rows, and for price, ram/storage and weight those two rows are outliers (one RM36,999 workstation, one 128GB/4TB config, one 3.73 kg desktop replacement), so price spread only 34 points across the catalog against gpu's 77 — the presets were weighting eight factors as though they shared a scale. A gaming laptop consequently scored highest on Office & Study. `_normalize` still falls back to min-max when a range carries no `values` list (the global-benchmark-table fallback in `get_laptop_ranges`), so the engine cannot fail on a partially populated ranges dict.

Two consequences worth holding on to. **Scores now drift with catalog composition** — one addition moves any percentile by at most 0.4 points across 238 laptops, but regeneration cadence matters in a way it did not before; regenerate via `POST /laptops/pick-scores/generate-all` after any catalog change, not just after benchmark or weight-profile changes. And **the number is a percentile**, so the UI should say "better than 62% of the catalog", not "62 out of 100". `python -m app.scripts.simulate_normalization` is the independent check: it monkeypatches `_normalize` and identifies the factor by the `(min, max)` pair inside the range dict handed to it, so **changing `_normalize`'s signature breaks that script** — update it in the same change, since it is the only thing that can verify the engine against the ADR's evidence.

**Recommendation pipeline** (`app/recommendation/service.py`): hybrid vector search → batch PickScore → Gemini `gemini-3.5-flash` with `with_structured_output(_LLMOutput)`. Requires an existing `laptop_user_preference` row (returns 400 otherwise). Default `top_k = 3` (candidates pool = 15). LLM language level is driven by user's `tech_savviness` field.

**CRS pipeline absorbed into the agent** (`app/rag/` + `app/agent/tools/search_laptops.py`): the 5-module pipeline — retrieve (top-50 pgvector) → rerank (`final_score = similarity × penalty + bonus`) → relax (stepwise: weight first, then budget) → gate (calibrated threshold `0.53` — embedding-model-specific, re-derive on any embedding model change; see `app/rag/gating.py`) — is called directly from the `search_laptops` agent tool instead of running as a separate, fixed-order chat pipeline. There is no standalone intent-detection call anymore; the LangGraph agent decides per turn, from full conversation context, whether to call `search_laptops` again or answer from the existing `conversation_laptops` pool. On a gated (low-confidence) result the tool returns no laptops plus a `bottleneck`/`message` pair, and the agent — not the tool — is responsible for turning that into a clarifying question rather than a dead end. Every `search_laptops` call still writes to `pipeline_eval_logs` (DB) and `logs/eval/pipeline_trace.jsonl`. `UserConstraints` is a decoupled dataclass — not tied to `LaptopUserPreference` — built directly from the tool's own args (`budget_max`, `brand`, `purpose`). **Only `status == "active"` laptops are recommendable**: the filter lives in `app/rag/retrieval.py` (both the pgvector query and `_relational_fallback`) rather than in the tool, because relaxation retries and `rag/evaluation.py` re-enter through the same function — putting it in `search_laptops` would leave those two paths unfiltered. The persisted `conversation_laptops` pool is filtered on read at all three of its surfaces — `graph.py::_pool_block` (the agent's answer-from-memory path, and therefore the one that could otherwise *recommend* a retired laptop), `agent/router.py`'s card payload, and `GET /conversations/{id}/laptops` — so a laptop deactivated mid-conversation drops out of the thread instead of lingering. The pool *rows* are left in place; the filter is on read only.

**The configuration step must not ask a question the source material cannot answer** (`app/reviews/config_evidence.py`, `link_service.separability`, `GET /reviews/families/{id}/configs`). The step asks which configuration a reviewer tested, and for most videos nothing on the screen could answer it: a title like *"Asus ExpertBook Ultra: The First Panther Lake Laptop I Strongly Recommend"* names no CPU, GPU or RAM, so answering honestly meant watching the video — minutes per review, on a queue budgeted for ten seconds each. Three changes, in order of how much they matter.

**`separable` can cancel the question outright.** When a family's remaining differing columns are only `ram_gb`/`ssd_gb` (`_UNSTATEABLE_COLUMNS`), the configurations are indistinguishable from any review — no reviewer states whether their unit had 32GB or 64GB, and no conclusion in the video would change if they did. The screen must then render **no chooser at all**, show `separability_reason`, and leave the selection null. This is not a UI preference: four options where the discriminating information cannot exist invites a guess, and **a guessed `laptop_id` is strictly worse than a null one** — null reads downstream as "configuration unknown", a guess silently attaches that video's performance claims to a machine nobody tested. It is the same principle that made ADR-0012 family-first, applied to the one screen still asking anyway. Branch on `separability_code` (`separable` / `ram_storage_only` / `single_config` / `identical_specs` / `no_configs`), never on the prose: `single_config` means "nothing to choose *between*" and a screen may still offer that one row, while `ram_storage_only` means the question has no answer. `no_configs` is reachable and is not a data error — ExpertBook P3 G2 is two rows and both are suspended, so the filter empties the family.

**`evidence` turns investigation into confirmation.** Pass `?review_id=` and the endpoint scans the video description and stored transcript for spec strings belonging to *these* members, returning each hit with surrounding context and, for transcript hits, the second it was said at. Probes come from the catalog rows, never from a general spec vocabulary — a "find any CPU" scan would report a comparison video's competitor chip as evidence about this family. A probe must also be specific enough to trust: the alphanumeric part number (`358H`, `B390`, `i7-1370P`) is preferred, a bare numeric token is **never** used alone (`430` matches prices, view counts and timestamps), and an anchorless string like `"Intel Graphics"` yields no probe at all — it identifies no specific part, so it would match every member at once. Transcript text is joined before searching, because YouTube splits segments on timing and a probe routinely straddles two. `found_nothing: true` is a real answer meaning *stop looking*, and is deliberately distinct from having no source material at all (`sources_available`). Measured on the current 88 rows: Chinese-language channels do paste full spec tables into descriptions, which is what makes the description the richer of the two sources and why `POST /reviews/backfill-descriptions` exists — every row predates the column, so without it the feature would be blind on the entire existing queue.

**The table is computed over the survivors, not the family.** Suspended rows are excluded (`family_members(..., exclude_statuses=)`) and `differing_columns` is then recomputed — that ordering is the point, not an implementation detail: on the ExpertBook Ultra family, dropping the suspended RM 0 row collapses price to a constant 11999, so a column that only looked discriminating because of placeholder data stops being offered. `inactive` is deliberately **not** excluded anywhere: a delisted laptop is the normal subject of an old review, and hiding it would make those reviews unlinkable. `excluded_suspended` reports what was withheld so a row vanishing from yesterday's list has an explanation on the page. `config_row` returns a readable `label` ("Ultra 7 358H / Arc B390 / 32GB / 1TB") and **no longer returns `model_code`** — a slug like `asus-expertbook-ultra-b9406caa-ultra7-358h-arcb390-32gb-1tb` is a database key that duplicates, illegibly, the four columns sitting beside it.

**`irrelevant` is a dismissal, and dismissal means marking, not deleting** (`ReviewStatus.IRRELEVANT`, `PATCH /reviews/raw/{id}/irrelevant`): dropping the `review` keyword from discovery bought recall on Chinese-titled videos — Chinese channels do not title in English — and the price is non-laptop videos reaching the human queue. `irrelevant` is how they leave it, and it is **not** a flavour of `rejected`: `rejected` means the video is about a laptop but has no transcript and is a retry candidate, `irrelevant` means it is not about a laptop and never will be. Merging them would recreate the cause ambiguity the `failure_reason` split removed.

**Deleting the row is self-defeating and must not be offered as an alternative.** `video_id` is UNIQUE and `service.should_skip_existing()` — the predicate `ingest_for_laptop` calls — leaves every existing non-`rejected` row untouched, so a deleted row is rediscovered and reinserted on the next ingest run and lands straight back in the queue. The row *is* the dismissal. Same reasoning as the 15 terminal `no_track` rows: keeping them is how ingest knows not to retry. That predicate was extracted from the loop specifically so this can be asserted without a DB or a YouTube call (`tests/test_ingest_skip.py`, the repo's first pytest suite — `pytest tests/ -q`); its last case asserts that *only* `rejected` is ever rewritten, so a future status member has to make that decision explicitly.

The transition is **restricted to `pending` ⇄ `irrelevant`** (409 from anything else) and is idempotent. Undo has exactly one destination, `pending`, so admitting a `matched` or `rejected` row would mean restoring it as `pending` and silently discarding a match or a transcript-failure verdict. `GET /reviews/pending` filters on `status == pending`, so dismissed rows drop out with no extra clause; the undo surface is `GET /reviews/raw?status=irrelevant`. `GET /reviews/pipeline-status` reports `link.irrelevant_total` / `reviews_total` / `irrelevant_ratio` — the **ratio** is the point, not the count: it measures what dropping the keyword cost. ~10–15% says the recall was worth it; ~40% says discovery is too loose and wants `laptop`/`notebook` added as a term — *not* `review` back, which would reintroduce the original problem.

**Transcript failures are typed, and the split that matters is terminal vs retryable** (`app/reviews/transcript.py`, migration `8e429682f918`): `fetch_transcript()` returns a `TranscriptResult` dataclass (`segments`, `failure`, `language_code`, `is_generated`), never a bare `None`. `TranscriptFailure` has five members; `TERMINAL_FAILURES = {NO_TRACK, VIDEO_UNAVAILABLE}` means no language preference, no proxy and no retry can ever recover that video — it is the ASR decision set. `IP_BLOCKED`, `NETWORK` and `UNKNOWN` are operational and **must not be counted as a data gap**. The old blanket `except Exception: return None` collapsed all five into one outcome, which is precisely why the `rejected` bucket's dominant cause was invisible: an audit of all 39 rejected rows (2026-08-22) found **48.7% had an English track all along** (transient/proxy failure at ingest), 38.5% genuinely had captions disabled, and only 12.8% were the Chinese-only case. `service.py` persists the reason to `raw_youtube_reviews.failure_reason`, the chosen track's code to `transcript_language`, and counts tries in `transcript_attempts`.

Two collaborating details. **Language is matched by family prefix, not literal code** — `_LANG_FAMILIES = ("en", "zh")` compared against `language_code.split("-")[0]`, because `fetch()`'s default is the exact string `('en',)` and a video whose only English track is `en-US` therefore raised `NoTranscriptFound` (a real case in the audit). **`_pick_track` prefers manually-created captions over auto-generated ones** within each family: ASR mis-hears product names, and product names are exactly what the matcher keys on. It deliberately does not `.translate()` a Chinese track — the chunk processor paraphrases downstream anyway, and translating at fetch time destroys the original wording irrecoverably.

`POST /reviews/retry-transcripts?limit=` re-fetches only rows whose failure was non-terminal. It costs **zero YouTube quota** (the transcript endpoint is unmetered), which is why it is separate from ingest, where a retry would first pay 100 units per channel for a search it does not need. Rows with `failure_reason IS NULL` are included — they predate the column, so their reason was erased and cannot be assumed terminal; expect the first run to reclassify a batch of them as `no_track` permanently. A recovered row goes to `pending`, **not** `matched` — the transcript says nothing about which laptop it is.

**Two read-only audit scripts back these numbers** (`app/scripts/`, both `--help`-documented): `audit_transcript_availability.py` re-opens every `rejected` row with `.list()` and buckets it NO_TRACK / NON_ENGLISH / HAS_ENGLISH / OTHER_FAILURE (`--sample N` bounds network calls; note the library raises `TranscriptsDisabled` rather than returning an empty list, so that exception counts as NO_TRACK). `audit_match_ties.py` recomputes the top-5 match candidates per review and reports the rank-1/rank-2 gap, splitting ties into same-family (config ambiguity) vs cross-family (real matcher failure) and CJK vs ASCII titles. Its 2026-08-22 baseline: **89.4% of videos are decided by a true tie** (`process.extractOne` returns the *first* maximum, so the winner is database row order), 34.2% of those spanning different families, 11 tied *and* above `MATCH_THRESHOLD`; CJK titles tie 95.2% of the time with 55% cross-family, because `token_set_ratio` splits on whitespace and Chinese has none. Re-run both after any matcher or transcript change. On Windows set `PYTHONUTF8=1` or CJK titles print as mojibake.

**Laptop families — one product line, many rows** (`app/laptops/family_*.py`, `laptop_family` table, migration `e2c76b019f4d`): the catalog stores one row per configuration, so a single machine occupies up to 14 rows and could otherwise fill five of six shortlist slots on its own. `laptops.family_id` (nullable FK) groups them, and two consumers deduplicate on it — `search_laptops` (after the gate, **before** the `_MAX_RESULTS = 6` slice) and `get_ranking_for_use_case` (before the limit slice). Deduplicating after the cut would just return a shorter list of the same one product.

*A family is a COARSE product line*, at the granularity a manufacturer segments its own catalog by — not a configuration, not a chassis code, not a model year. Apple has three: MacBook Air (13 and 15 together), MacBook Pro (14 and 16 together), MacBook Neo — size is not a product boundary there because the chip tiers overlap between Air and Pro. Every ROG Strix is one family (Strix G16, SCAR 16, SCAR 18). A family spanning two model years or a wide price range is therefore *expected*, not a defect: the dedup rule picks the member nearest the stated budget (`family_service.closest_to_budget`), so one family answers a RM 5,000 question and a RM 9,000 one with different configurations.

*`family_key` is a seed, not an identity.* `family_key.py` proposes a grouping by truncating `product_name` at the first paren — the same function the YouTube review pipeline searches by, deliberately shared so the two cannot drift. At product-line granularity it **over-splits** ("asus vivobook 14" vs "vivobook 14", every Acer SKU whose model code sits outside the parens), so several seed keys legitimately map to one family. Hence: **`laptop_family.family_key` is NOT unique**, it is provenance only, and nothing may resolve a family by matching on it — after a merge the family carries one of the two keys and key equality would strand every future member of the other.

*Matching a new laptop* (`family_service.resolve_family_id`, called from the AI processor's insert branch and `POST /laptops/`): compute its seed key, find laptops that already share that key and already have a family, adopt theirs. If they disagree, or there are none, **leave `family_id` null**. Guessing is strictly worse — a null passes through dedup untouched and shows up as backlog, while a wrong family hides a machine invisibly. The processor's upsert dict carries no `family_id`, so re-processing a scraped page never moves a laptop an admin placed by hand.

*Merging is a human action, through the CRUD.* `POST /families/regroup` (admin) runs `regroup_unassigned`, which touches only `family_id IS NULL` rows — safe to re-run, and structurally unable to undo a merge, because a merged family's members are no longer null. It seeds a starting point (98 families from 274 laptops on the 2026-08-19 catalog); merging up to the product line is `POST /families/{keeper}/laptops` to move the members, then `DELETE` the emptied family. **Bulk moves go through `family_service.move_laptops`**, shared by that route and `POST /families/laptops/move` — the destination-in-the-body twin, which is what an admin screen's checkbox column calls: it moves a selection from any mix of source families, takes `target_family_id: null` to release the selection to unassigned (required field, never defaulted — releasing must be stated, not forgotten), and returns `emptied_families`, the source families the move left at zero, i.e. the exact list of `DELETE`s that finish the merge (it never deletes them itself). Both are all-or-nothing: one unknown laptop id 404s and writes nothing, so a typo cannot half-apply a merge. `DELETE /families/{id}` **releases** members to null rather than cascading — unlike a brand delete, which 409s — because releasing is the second half of every merge and null is a safe state. `python -m app.scripts.backfill_families` prints the same three counts and calls the same function; its Part 3 (over-splits) is the merge worklist, Part 2 (over-merges) is informational at this granularity.

**Every ordering that can tie ends on a unique column.** Sibling configurations of one machine tie constantly — same product name, near-identical embeddings, same PickScore, same price — and an unbroken tie falls through to database return order, which Postgres does not guarantee. Left alone, the shortlist reshuffles between identical requests and family dedup picks a different representative each time. Fixed at every stage: `retrieval.py` (both queries), `reranker.rerank` (`(-final_score, laptop_id)`), `get_ranking_for_use_case` (`(proxy, -score, price_rm, id)`), and `sorting_service.apply_sort`, which grew a `tiebreak=` parameter — pass the primary key on any route that paginates, or a tied row can appear on two pages or on neither.

**Taxonomy split — `product_types` vs `categories`**: two separate small lookup tables in `app/taxonomy/`, not one merged table — they serve different admin workflows. `product_types` is a small, stable set (product line: laptop today, phone/other 3C later) that scopes `questionnaire_questions`. `categories` is dynamic, frontend-facing marketing/use-case tags (Gaming, Business, Creator, etc.), many-to-many with `laptops` via the `laptop_categories` junction table (added with zero changes to the already-complex 200+ field `laptops` model). **Three relationships map `laptop_categories`** — `Laptop.categories` and `Category.laptops` (the `link_model` pair) plus `Laptop.category_links` (mapped directly at the junction so deleting a laptop cascades its rows away). SQLAlchemy warns on every `configure_mappers()` about the overlapping writes unless both `Laptop.category_links` and `Category.laptops` carry a matching `overlaps=` kwarg — they do, and the pair must stay in sync. `category_links` deliberately has **no** `passive_deletes`: that would delegate the junction rows to a DB-level `ON DELETE CASCADE` which does not exist on `laptop_categories.laptop_id` and one-to-many with `laptop_customizations` (`category_id`, migrated off a free-typed string that had drift risk).

**`LaptopUserPreference.budget` is a `{min, max}` JSON range, not a single ceiling**: the v1 questionnaire's budget question is range-bucketed ("< RM 2000" … "> RM 5000"), so a single ceiling int couldn't represent the open-ended top bucket without a fabricated cap. `max: null` means no upper limit. `app/pickscore/engine.py::_score_price()` reads `budget["max"]` only — `min` is stored and consumed nowhere in scoring. That is an open product question, not an oversight: with `max: null` (the open-ended "> RM 5000" band) a user who said they have a high budget falls through to the plain catalog curve, which rewards cheapness. Decide whether a floor should lift the score of a more expensive machine before building it.

**Windows Playwright compatibility**: All async Playwright calls are offloaded to a dedicated worker thread with its own `ProactorEventLoop` via `app/scraper/playwright_utils.py`. This prevents event loop conflicts with Uvicorn's default `SelectorEventLoop` on Windows.

**Asus scraper dual-path**: ROG pages (`rog.asus.com`) read `window.__NUXT__.state.Spec.spec`; standard ASUS pages (`www.asus.com`) read `window.__NUXT__.state.PDPage`. Both return a `list[dict]` — one entry per SKU variant — with `?v=N` URL suffix for multi-variant pages.

**Acer — parsed from uploaded HTML in the DB, no network at all** (`app/scraper/acer_scraper.py`): this brand is not scraped live. Product pages are saved by hand from a normal browser, POSTed to `/scraper/upload-html`, stored in `raw_product_htmls`, and parsed from that string with lxml. Both public entry points keep their shape (they just take a `Session` now), so `router.py` and `bulk_scraper.py` dispatch to it exactly like any other brand. There is no on-disk HTML — the container filesystem is ephemeral, so saved pages had to live in Postgres to survive a deploy.

*Why offline* — `store.acer.com` sits behind Akamai Bot Manager, and every automated route was tried and refused (measured 2026-08-05):
- It fingerprints the **TLS/HTTP2 handshake**. Playwright's *bundled* Chromium dies with `ERR_HTTP2_PROTOCOL_ERROR` on every request regardless of user-agent or flags.
- **curl_cffi TLS impersonation** (real browser JA3/JA4 + HTTP2 SETTINGS) fixes exactly that layer — the site root returns a full 200 — but protected paths still return `403 Access Denied` from `AkamaiGHost`, because the `_abck` cookie stays unvalidated (`~-1~`) until Akamai's obfuscated sensor JS posts telemetry. Note `firefox*` profiles pass the edge where `chrome*` profiles get 403; curl_cffi's Chrome fingerprints lag real Chrome, and a Chrome UA over a near-miss Chrome handshake is itself a signal.
- **Real Google Chrome via Playwright** (`channel="chrome"`) gets the challenge interstitial or 403 too, and is IP-reputation-sensitive — a datacenter IP (Render) has no chance. The Dockerfile's `playwright install --with-deps chrome` was removed with the browser path; `chromium` remains for Apple/ASUS.
- `robots.txt` also disallows `/en-my/*?*`, covering both `?product_list_limit=all` and `?p=N` pagination, so even a permitted crawl would only see 10 of 49 products; the `en-my` product sitemap is broken (returns a binary blob).

*The upload → parse workflow* — a saved page identifies itself by its `<link rel="canonical">` (Magento emits it, and `og:url`, on every product page), so **filenames are irrelevant**. `POST /scraper/upload-html` (multipart; `/upload-html/json` is the JSON twin) extracts that URL, resolves it to a queued `laptop_scrape_urls` row, upserts the HTML, and moves the target to `html_uploaded`. Matching is exact-URL-first then by slug (`html_ingest.py::url_key`), so a trailing slash or query string on either side still matches. Every item is independent — a page with no canonical tag, or one belonging to another brand, is reported in the summary (`matched`/`unmatched`/`invalid` counts plus per-file rows) and never aborts a 49-file batch; the batch commits once at the end. Re-uploading upserts on `canonical_url` (unique) and re-queues the target, which is how a stale price is refreshed — duplicates *within* one batch are absorbed by autoflush, not an IntegrityError.

Then `POST /scraper/bulk-scrape` (or `/scrape-targets`) parses: `scrape_acer_laptop_specs(url, brand_id, session)` reads the stored string via `html_ingest.get_raw_html()` and returns the same dict shape as any brand scraper. A target with no uploaded HTML returns `status: failed` telling you to upload it, and a page captured while Akamai was showing its challenge is reported as "no spec rows" — both per-target, never fatal to the run. **`laptop_scrape_urls` is the work list** (`GET /scraper/targets?brand_id=…&scrape_status=failed`). `crawl_acer_specs_links()` now lists the canonical URLs that have HTML stored, so it only needs re-running to enqueue a product not already in the queue.

*Status lifecycle* (`ScrapeStatus` in `app/scraper/models.py`; plain VARCHAR, so new values need no migration): live scrape is `pending → completed/failed/skipped`; upload brands are `pending → html_uploaded → parsed/failed`. `parsed` is kept distinct from `completed` so the admin UI can tell a hand-uploaded page from a live scrape — `bulk_scraper._success_status()` picks between them off `HTML_UPLOAD_BRANDS`. **`html_uploaded` is in `run_bulk_scrape`'s WHERE clause alongside `failed`**: a target that failed for want of HTML already has `last_scraped_at` stamped, so without that clause fresh HTML would never be re-picked.

Pages are Magento *simple* products (one SKU per page, no swatches), so the scraper always returns a single-element list with an empty `source_url_suffix`. Specs come from `#product-attribute-specs-table`, section-prefixed (`"Processor & Chipset / Processor Model"`) since section header rows carry a `▶` and an empty `td`. Price must be picked by explicit `data-price-type` (`finalPrice` → `basePrice` → `oldPrice`) — pages also carry an **empty-type** node holding an instalment figure, so first/last-match picks the wrong number. Gallery images are read from the `mage/gallery/gallery` JSON inside the page's `x-magento-init` script, **not** from `.fotorama__img` nodes — those are built client-side and do not exist in saved HTML, and the JSON is the same source they would have been built from. Still filter to `/media/catalog/product/` (drops promo banners) and strip `?` (collapses the same photo served at several sizes).

**AI Processor model**: `gemma-4-31b-it` via `ChatGoogleGenerativeAI` (LangChain). Free-tier limits: **15 RPM, 1500 RPD, and a strict 16,000 input-TPM cap** (Google added the TPM cap — it, not RPM, is the binding limit for high-context calls). The processor enforces a 5-second inter-request delay and a default batch of 100 per run (~8 min) to stay safely under 15 RPM; its per-request prompts are small enough that 16k input-TPM is not usually binding there, unlike the eval harness. Hard ceiling is 1500 per run (`?limit=1500`). AFC (Automatic Function Calling) is enabled by the Google SDK — it self-corrects structured output against `ExtractedLaptopFamily` for up to 10 rounds per request.

**AI Processor safety rules**: The Gemini prompt enforces combinatorial safety (base configs first) and price matrix isolation (output `0.0` for upgrade prices not explicitly stated) to prevent hallucinated pricing. Duplicate SKUs are handled via an explicit **upsert**: query by `model_code` first — if exists, update all fields in-place and record price history only if `price_rm` changed and is non-zero; if new, insert and record the initial price snapshot. `model_code` is never overwritten during an update (it is the lookup key).

**Auth scopes**: JWT tokens are scoped — `email_verification` (1hr), `password_reset` (15min), and standard access tokens (7 days default). The `get_current_admin` dependency enforces `role == "admin"` (403 otherwise).

**Hybrid vector search** (`POST /laptops/hybrid-search` in `laptop_router.py`): embeds the user query with the same embedding model used for the documents (via `embed_text()`), then runs a single SQL statement that joins `laptops` ↔ `laptop_embeddings` ↔ `laptop_brands`, orders by pgvector cosine distance (`<=>`, ascending = closest), and applies optional `budget_max`/`brand` hard filters in the same query. Distance is converted to `similarity_score = 1 − distance` in the response (higher = better). Returns a ranked candidate pool (`LaptopSearchResult`) intended to feed the downstream rerank → PickScore → LLM stages.

**Price history**: `Laptop` price is captured into `laptop_price_history` in three places: (1) `POST /laptops/` router on manual create, (2) `PUT /laptops/{id}` router when `price_rm` changes, and (3) the AI processor (`app/processor/engine.py`) on every new insert and on re-process when `price_rm` changes and is non-zero. `GET /laptops/{id}/price-history` returns the ordered series. This prevents vendor price changes from being silently lost and backs the planned Price History Tracker chart.

### PickScore Engine (`app/pickscore/`)

Fully deterministic scoring engine — no LLM involvement, no product-specific imports. Produces a structured breakdown consumed by the LLM for conversational explanations. Designed to be reused across any 3C product category (laptops, phones, tablets) via an adapter pattern.

**Files:**
- `engine.py` — 8 factor scoring functions + 3-layer weighting pipeline + `calculate_pick_score(product: ScorableProduct, ...)`
- `schemas.py` — `ScorableProduct` dataclass (product-agnostic input contract), `PickScoreResponse`, `BatchPickScoreResponse`, `FactorBreakdown`
- `benchmark_service.py` — RapidFuzz fuzzy matching against benchmark tuples; module-level 5-min cache keyed by normalized model string; confidence threshold 0.6
- `ranges_cache.py` — Generic TTL cache (`get_cached_ranges` / `set_cached_ranges`); no DB queries — callers own the query logic

**Laptop adapter (`app/laptops/`):**
- `pickscore_adapter.py` — `laptop_to_scorable(laptop, brand_name) → ScorableProduct`; `get_laptop_ranges(session) → dict` (queries `laptops`, `cpu_benchmarks`, `gpu_benchmarks`; uses the generic ranges cache with key `"laptop_ranges"`)
- `pickscore_router.py` — `POST /laptops/calculate-score` and `POST /laptops/calculate-score/batch`; owns `LaptopPickScoreRequest` and `BatchLaptopPickScoreRequest` schemas

**Adding a new product category (e.g. phones):**
1. Create `app/phones/pickscore_adapter.py` — implement `phone_to_scorable()` + `get_phone_ranges()`
2. Create `app/phones/pickscore_router.py` — `POST /phones/calculate-score` using the same `calculate_pick_score()` from `app/pickscore/engine.py`
3. Register router in `app/main.py`

**Two modes:**
- **Personalized** — triggered when `user_id` is provided and `laptop_user_preference` exists; uses the user's `priorities` dict (factor → weight 1–10), `purpose` list, `portability` intensity, `budget`, `screen_size`, and `brand_preferences`
- **General** — triggered when `user_id` is null; uses `DEFAULT_PRIORITY` (N-i rule, 8 factors), neutral modifiers, inverse percentile for price, fixed 50 for brand/screen size. `calculate_pick_score(..., priority_override=...)` lets general-mode callers swap `DEFAULT_PRIORITY` for a custom base-weight profile (ignored in personalized mode — a real user's priorities always win).

**Precomputed use-case scores (`app/laptops/pickscore_general.py`)**: the `laptop_pick_scores` table stores one general-mode score per laptop × use case (unique on `laptop_id + use_case`), with the full factor `breakdown` + `flags` as JSON. The `LaptopPickScore` class itself lives in `laptop_models.py` (see "Circular import resolution") and is re-exported here; `pickscore_general.py` owns the weight profiles and generation logic. Five use-case weight profiles in `USE_CASE_PRIORITIES` (slugs: `office_study`, `programming`, `gaming`, `creative_work`, `general_use` — the frontend's use-case cards; `general_use` is an explicit price-first all-rounder profile, NOT `DEFAULT_PRIORITY` — the N-i rule gave GPU ~17% weight for daily use). Scores are deterministic — regenerate via admin `POST /laptops/pick-scores/generate-all` after processor imports, benchmark refreshes, or profile changes. Public reads: `GET /laptops/{id}/pick-scores[?use_case=]` and `GET /laptops/pick-scores/ranking?use_case=&limit=`. Ranking caveat: for `gaming` only, rows flagged `gpu_score_is_proxy` (Apple, integrated graphics, or unresolved) sort after all real-benchmark laptops, because a proxied GPU score says nothing about gaming performance.

**8 scoring factors (all output 0–100):**

| Factor | Key logic |
|---|---|
| `price` | Inverse percentile against the catalog in **both** modes; a personalized `budget["max"]` scales that base by `max(0, 1 − 2 × overRatio)` once the price is over it (zero at 50% over). See "One price curve" below |
| `cpu` | `normalize(cpu_mark)` via benchmark service |
| `gpu` | `normalize(gpu_mark)`; three paths set `flags.gpu_score_is_proxy=true` — Apple (CPU proxy), integrated graphics (resolved via the CPU's iGPU), unresolved (neutral 50). See "GPU resolution has three proxy paths" |
| `ram_storage` | `ramScore×0.6 + storageScore×0.4`; HDD storage gets `−15` penalty |
| `portability` | Inverse normalize on `weight_kg` (cheapest laptop-weight rank = 100) |
| `battery` | Normalize on `battery_wh` |
| `screen_size` | Bucket distance (≤14"=0, ≤16"=1, 17+"=2); `score = max(0, 100 − distance×40)` |
| `brand` | 100 if brand in `brand_preferences`, else 50 |

**3-layer weighting pipeline:**
```
finalWeight[f] = baseWeight[f] × purposeModifier[f] × portabilityModifier (portability only)
normalizedWeight[f] = finalWeight[f] / sum(finalWeight)
```
Purpose modifiers (capped at ×1.3): Gaming→GPU×1.3/CPU×1.1, Creative→GPU×1.3/RAM×1.2, Programming→CPU×1.2/RAM×1.2, Office→CPU×1.1. Portability multipliers: Yes→×1.4, Neutral→×1.0, No→×0.5.

**Batch endpoint** (`/laptops/calculate-score/batch`) fetches ranges and benchmark data once, then scores all laptops in the pool reusing the same cached data.

**Standalone script caveat (resolved)**: importing `LaptopUserPreference` — or any single laptop model — in isolation used to need a manual `from app.laptops.customization_model import LaptopCustomization` first, or mapper resolution failed. The bottom-of-module deferred imports described under "Circular import resolution" make every model module self-sufficient, so scripts no longer need the workaround; keep it that way when adding relationships.

### Scraping Status Flow

**`ScrapeTarget.scrape_status`** (`laptop_scrape_urls` table): `pending` → `completed` / `failed` / `skipped`
- Set alongside `last_scraped_at` in `_update_target()` in `bulk_scraper.py`
- `completed` — at least one variant saved to `raw_scrap_laptops`
- `failed` — scraper raised an exception OR zero variants saved; **automatically retried on the next bulk run** (WHERE clause picks up `scrape_status = 'failed'` in addition to `last_scraped_at IS NULL`)
- `skipped` — URL already had entries in `raw_scrap_laptops`; stamped but not re-scraped

**`RawScrapLaptop.processing_status`** (`raw_scrap_laptops` table): `pending` → `processing` → `completed` / `failed`

Bulk scrape queries `is_active=True` AND (`last_scraped_at IS NULL` OR `scrape_status = 'failed'`). Returns HTTP 207 on partial failures; writes timestamped failure logs to `logs/scraper/`.

### Deployment

`.github/workflows/deploy.yml` on push to `main` (doc-only changes excluded via `paths-ignore` — note the key is `paths-ignore`, **not** `path-ignore`, which GitHub silently ignores):

1. **build-and-push** — builds the Dockerfile and pushes to GHCR (`:latest` + `:sha`). `docker/setup-buildx-action` is required before the build step: the `type=gha` layer cache only works with the docker-container buildx driver, and the build fails without it.
2. **deploy** — hits the Render deploy hook (`secrets.RENDER_DEPLOY_HOOK`); Render pulls the image and restarts.

Dockerfile runs as non-root `appuser`; `WORKDIR /app` itself stays root-owned, so any runtime-writable directory must be created and chowned explicitly before `USER appuser` (currently `/app/logs`). The container startup command runs `alembic upgrade head` before uvicorn, and binds `${PORT:-8000}` (Render injects `PORT`). `docker-compose.prod.yml` is a VPS alternative that pulls the GHCR image; its `./logs:/app/logs` bind mount requires the host dir to exist and be writable by UID 1000, or file logging falls back to console.
